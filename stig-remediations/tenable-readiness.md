# Authenticated compliance baseline: diagnosis and evidence

Use this runbook for the single authorized Windows asset. Resolve its identity, address, scanner and scan/history identifiers privately. A finished scan with zero vulnerabilities and no audit results is **inconclusive**, not a compliance pass. Nothing here authorizes a scan or host change.

Original API checkpoint, November 13, 2026: the owned run completed in 63 seconds and reports zero hosts, zero compliance rows, zero vulnerability rows and no result notes. Its original 16,933-byte export was downloaded and hash-verified: one report, zero `ReportHost` elements and zero `ReportItem` elements. The extractor rejected it with `exactly one authorized host is required; empty is not a pass`. That history contains no recorded host assessment from which to establish Windows authentication or compliance. Its empty results do not identify Remote Registry as the cause. The private evidence alias is `EV-TENABLE-API-20261113`.

Scoped metadata reads found the assigned scanner online and a reported address. That address alone is not proof of its source as seen by the target. The original/restored configuration has fast discovery enabled, TCP/ICMP/ARP discovery, SYN scanning, automatic dependencies, silent dependencies and no audit trail. Fresh editor inspection established that 21156 was the only explicitly enabled individual plugin; discovery/dependency helpers in the export are a different representation. The configured Windows credential instance and selected V2R11 audit were preserved without reading credential secrets.

One subsequent, explicitly approved diagnostic history completed in 387 seconds, including orchestration; plugin 19506 reports 260 seconds of engine activity. The current VM address matched the saved target. Its 27,955-byte export contains one host and four informational results (10940, 19506, 56984, 64814), including RDP/TLS observations. At that checkpoint this proved a service path to that VM, but not SMB access. Plugin 19506 reports `Credentialed checks : no`; there are no SMB login, registry-access or 21156 results. All ten controls remained unassessed at that checkpoint. The parser processed the actual populated diagnostic export successfully, retaining its unverified claim. Evidence alias: `EV-TENABLE-DIAGNOSTIC-20261113`.

The diagnostic bypassed liveness ping, restricted SYN port discovery to TCP445, disabled local port enumeration, exposed dependency output, and selected narrow diagnostic plugins plus Service Detection 22964. Automatic plugin dependencies can perform their own service probes: this run produced TCP3389 results despite the port-discovery range. Do not describe the port range as a complete network-traffic allowlist. No whole plugin family was enabled. Tenable normalized fast discovery to `no` when its parent ping setting was disabled; the readback guard stopped launch until this was explicitly reconciled. The original affected settings, plugin selections, schedule and protected metadata were restored and verified after one launch. No Windows settings changed.

Existing guest observations confirm SMB/RPC listeners and a disabled/stopped Remote Registry service. Firewall packet logging was off and no matching scan-account authentication or SMB-block events were found in the bounded window. Absent logs do not establish absence of packets. Host filtering was the leading explanation for the SMB gap; port-specific upstream filtering had not been excluded. The diagnostic changed several settings, so it does not uniquely isolate the original zero-host cause. Requested audit-trail settings were saved, but the result API exposed neither an audit trail nor a knowledge base; skipped-plugin explanations remain unavailable.

The later authorized prerequisite batch established an authenticated V2R11 baseline, followed by ten controlled remediations and an equivalent authenticated follow-up. Both assessed one host, reported credentialed checks **yes via SMB**, and returned SMB-login, registry-access and 258 compliance results. The ten exact catalog rules changed **FAILED → PASSED**. Both actual populated compliance exports now pass the corrected extractor. Temporary source-restricted ingress and Remote Registry changes were restored after each run, as were the original saved scan settings. See the [execution report](../docs/windows-stig-validation.md) for timing, residual findings and review gates. The original zero-host history still cannot establish a unique root cause.

## Distinguish the failure stages

Preserve the existing scan history before editing its configuration. Obtain target/host counts, start/end UTC, scanner status, warnings, credentialed-check status, audit selection and available diagnostic output. Read only this operator's scan; a shared scan's visibility does not authorize inspection or use.

| Stage | Evidence needed | Interpretation and next gate |
|---|---|---|
| Discovery | Requested target versus hosts assessed; scan history warnings; discovery methods and TCP port scope | Zero assessed hosts leaves authentication and compliance untested. Fast discovery is not proof of reachability. |
| Scanner path | Assigned scanner online/permission metadata; administrator-confirmed source and network path; target listener and applicable firewall state | A listening port on the VM or working Bastion does not prove scanner reachability. Do not inspect peer networks or run an unapproved connectivity scan. |
| Authentication | Plugin 19506 credentialed-check flag, 10394 SMB login and any authentication-error output | A successful login alone does not prove administrative registry access. Absence of a diagnostic plugin is unknown, not success. |
| Privilege and registry | 10400 registry access; 24786 insufficient administrator privileges; 26917 unavailable registry; 10428 incomplete enumeration | Check actual account identity, shares, services and token behavior before changing policy. Do not assume every local account needs a UAC exception. |
| Check execution | Plugin 21156, its dependencies and audit trail; 21745 local checks not run; 214001 compliance errors | Selected is different from executed. Capture skip reasons and distinguish missing prerequisites from a finding. |
| Audit | Exact audit filename/revision, plugin version, rule identifiers, applicability and per-control results | A catalog entry or selected audit name is not proof it ran. Warnings/errors remain inconclusive. |
| Reporting | Same scan/history/target in raw export and UI; export completion, SHA-256, truncation and result counts | Do not confuse vulnerability-only views or policy-only exports with complete compliance evidence. |

Diagnostic plugin meanings are documented by [Tenable](https://docs.tenable.com/whitepapers/useful-plugins/Content/UsefulPlugins/TroubleshootingPlugins.htm). Plugin [21156](https://www.tenable.com/plugins/nessus/21156) requires SMB credentials/transport knowledge and [dependencies](https://www.tenable.com/plugins/nessus/21156/dependencies) including registry access. Selecting only compliance checks can work when dependencies are enabled. Nessus documents `auto_enable_dependencies` and `silent_dependencies`; the latter can hide dependency output. Verify the actual configuration with the administrator rather than changing shared scanner settings. [Advanced scanner settings](https://docs.tenable.com/nessus/Content/SettingsAdvanced.htm).

Fast network discovery reduces additional verification after a host responds; it does not bypass all discovery or firewall controls. Review the actual discovery methods before proposing changes. Do not blindly repeat the same scan. [Discovery settings](https://docs.tenable.com/vulnerability-management/Content/Scans/DiscoverySettings.htm).

## Controlled prerequisite correction

Remote Registry, SMB access and adequate Windows privileges are prerequisites for registry-based Windows compliance checks. If the service is disabled and scan auto-start is off, that is a prerequisite gap even if a different earlier stage also failed. [Windows authentication requirements](https://docs.tenable.com/vulnerability-management/Content/Scans/Host.htm).

Disabled Remote Registry is **not the established cause** of the original empty scan. The successful authorized combination was a temporary exact scanner-source rule to this VM's TCP445 listener, Remote Registry Manual/start and the documented diagnostic settings. It worked for both baseline and follow-up, without widening the source, changing shared infrastructure or disabling the firewall. The earlier reported source was not a packet trace; the successful restricted path now supports its usability for these assessments. Fast discovery was already enabled in the original policy; enabling it again was not a correction. Future assessments need a new authorized prerequisite window because the temporary changes have been removed.

Prepare a separately approved batch with the exact host, confirmed scanner source, required ports, duration and recovery plan. Preserve initial service state/start mode and relevant rule definitions privately. Prefer a temporary, scanner-restricted rule on the owned VM when evidence requires it; never disable the firewall or change the shared NSG. Open additional RPC access only when the selected checks require it and the source/path is approved. Restore the service configuration and remove only newly created temporary rules at the agreed endpoint. Verify Bastion, agent health and security controls afterward. UAC, accounts, SMB1 and administrative-share auto-enablement are not default fixes.

Keep Safe Checks on, scheduling on demand, one target only, no public IP and scanner auto-modification options off unless separately authorized. Retain the Windows credential in Tenable's protected interface; never export it. Resolve domain/account formatting from the actual local/domain identity and diagnostics, not trial passwords.

## Automation access gate

Direct API access is working and is preferred for scoped scan operations. Original, diagnostic, authenticated baseline and follow-up histories and exports are preserved; the three later assessments each had one launch and one export request. The earlier temporary VM browser processes are stopped. A reusable official Chrome DevTools MCP/CLI connection on the coordination workstation supports authorized course/hunt reads and navigation. Browser access is separate from API authentication, Windows authentication and compliance evidence.

The current browser connection uses a local debugging endpoint and an explicitly started user process; no public debugging listener or automatic startup is configured. Its filesystem and application allowlists are safeguards, not browser-profile or operating-system isolation. Preserve authenticated sessions and restrict actions to approved applications. An ordinary prefilled sign-in may be submitted when authorized without reading its values; MFA and personal consent remain interactive. Never read cookies, tokens, saved passwords or browser storage to obtain API access. Operational configuration and browser-derived evidence stay outside Git.

An administrator can inspect **Settings → Access Control → Users → the assigned user → General → Authentication → API Key**, including permission to generate keys. For custom roles, **Platform → My Account → Read** permits viewing the keys page, whereas **Edit** includes generation. Check API access authorization and source-IP restrictions as well. Asset `CanScan` permission alone does not establish any of these. These are general access checks; the project's approved API authentication and owned-scan read/export-status access are now observed. [User administration](https://docs.tenable.com/vulnerability-management/Content/Settings/access-control/manage-users.htm), [custom-role privileges](https://docs.tenable.com/vulnerability-management/Content/Settings/access-control/custom-role-privilege-application.htm).

For the initial evidence batch, request only access to the owned scan. [Details](https://developer.tenable.com/reference/scans-details) and [history](https://developer.tenable.com/reference/scans-history) require Scan Operator plus Can View on that scan, or custom `VM.VM_SCAN.VM_SCAN.READ`; [export](https://developer.tenable.com/reference/scans-export-request) uses `VM.VM_SCAN.VM_SCAN.EXPORT` as the custom-role alternative. Viewing the [scan editor](https://developer.tenable.com/reference/editor-details) requires additional edit privileges even though it uses GET; the evidence client omits that endpoint. Broad asset permissions and browser login do not establish API access.

After administrator and operator approval, the human enters an approved key through the client's hidden terminal prompts. Key generation/replacement is a separate human action in Tenable; replacement can break existing integrations. Never put secret values in arguments, chat, logs, environment dumps or source files. The operator generated keys and entered both through protected hidden prompts. The client authenticated and privately preserved the owned scan's details/history. It did not generate keys.

The official [Tenable MCP server](https://docs.tenable.com/exposure-management/Content/getting-started/hexa-AI-MCP.htm) requires eligible Tenable One licensing, API keys and enabled MCP access. It is not an authentication bypass and is not connected here. A third-party browser service would introduce another access/data-sharing approval; it is not a way to inherit the current browser session.

Separately authorized metadata reads confirmed assigned-scanner availability, a reported address and the owned scan's editor configuration. Only allowlisted nonsecret projections were retained; scanner keys and credential values were not exported. The successful exact source-restricted SMB path is now observed for both authenticated assessments; it is not a general connectivity guarantee or packet trace. The reusable evidence client remains restricted to its original owned-scan/history/export routes; it has no scanner, credential or scan-editor enumeration action. A scan-specific credential does not establish a reusable managed credential; audit selection does not establish execution or revision coverage.

## Scoped evidence client

[tenable_client.py](tenable_client.py) uses Python's standard library and the official [API authorization](https://developer.tenable.com/docs/authorization) scheme. Its only network routes are details/history for one configured scan and that scan's existing-history export request/status/download. Export creation is an explicit POST that packages existing results; it does not launch a scan. The implementation contains no scan-create, edit, launch, delete, credential-enumeration or broad-inventory action.

Before connecting, review its source and authorize the integration. The nonsecret scope profile must contain exactly `scan_id`, `scan_name`, `target` and `scanner_name`, using privately confirmed values. `scan_id` can initially be null; protected setup asks for the numeric ID from the owned scan URL. No scan enumeration is needed. The current implementation deliberately accepts numeric scan IDs, even though Tenable also supports schedule UUIDs.

The operator performs setup once in an interactive terminal. Use an approved absolute private directory outside the repository, owned by the current user with mode 0700; scope and connection files use mode 0600. Setup refuses links, hardlinks, piped secret input and overwriting an existing connection. It asks for both API keys without echo, makes no network request, and writes a connection file containing the scope and credentials. This file is protected by filesystem permissions, **not encrypted**; it does not protect against root or other processes running as the same user. Keys retain their server-side permissions; the client's allowlist does not narrow the account's permissions.

```bash
python3 -B stig-remediations/tenable_client.py plan
python3 -B stig-remediations/tenable_client.py setup \
  --scope "$private_access/scope.private.json" \
  --connection "$private_access/connection.private.json"
```

After approved setup, the agent performs the ongoing evidence retrieval; the operator need not download each export. Every network action requires `--execute` and a fresh private output directory. Without that flag the following commands only describe the plan and do not read credentials.

```bash
python3 -B stig-remediations/tenable_client.py inspect \
  --connection "$private_connection" --output "$private_inspection" --execute
python3 -B stig-remediations/tenable_client.py request-export \
  --connection "$private_connection" --history-id "$confirmed_history_id" \
  --output "$private_export_job" --execute
python3 -B stig-remediations/tenable_client.py fetch-export \
  --connection "$private_connection" --job "$private_export_job/job.private.json" \
  --output "$private_download" --execute
```

Details must match the exact scan name, single target and scanner; alternate/tag targets, conflicting host identity and missing scope fields stop the operation. A compliance row without a hostname must bind by its exact host ID to the single IP-validated host in that same response; missing or conflicting bindings fail closed. This shape is covered by regression tests and both actual authenticated histories. History enumeration is limited to 50 complete entries; larger histories require a reviewed pagination change. Export requests require a terminal run. TLS certificate/hostname verification is enabled for the fixed origin; redirects, automatic retries and unbounded responses are refused. Errors omit remote bodies and headers. Before validating a returned export identifier, the client retains a bounded file-ID-only receipt beside the requested output directory, excluding response tokens. An existing receipt prevents another POST to that destination. Review a receipt after a failure; an uncertain export POST must not be repeated blindly. If status is `loading`, fetch the same job later. A `ready` response permits one private download, readback SHA-256 checks and a UTC manifest. Preserve incomplete artifacts on error for private review; do not treat a partial directory as completed evidence.

Raw responses/exports stay outside Git. Scan/history IDs remain positive numeric identifiers. Export IDs use a separate bounded ASCII path-segment validator: 1–128 alphanumeric, underscore or hyphen characters, starting with an alphanumeric character. Paths, query strings, percent escapes and whitespace are refused. Tenable documents these as strings in [export status](https://developer.tenable.com/reference/scans-export-status) and [download](https://developer.tenable.com/reference/scans-export-download). A live 47-character opaque ID exposed the earlier numeric-only assumption; its shape is covered with an independent synthetic fixture. Details/history, export status and completed download are now observed. The 16 MiB response limit, exact scope and host-identity checks remain. Do not relax them automatically on an unexpected response. A downloaded file still needs actual XML/target validation with the extractor below; an empty or unsupported export cannot become a compliance pass. Secret-literal checks supplement human review and do not establish comprehensive leak prevention.

## Offline export extraction

[nessus_summary.py](nessus_summary.py) reads the documented `.nessus` v2 XML structure and emits allowlisted metadata. It never contacts Tenable, writes files, launches scans or changes the [existing ledger](evidence-workflow.md). Its contract is grounded in Tenable's [v2 format specification](https://static.tenable.com/documentation/nessus_v2_file_format.pdf) and [current export documentation](https://developer.tenable.com/docs/export-file-formats). Actual empty-export rejection, populated diagnostic extraction, and complete authenticated baseline/follow-up compliance extraction are observed.

```bash
python3 -B stig-remediations/nessus_summary.py "$private_export" \
  --target "$authorized_target" --origin authorized-live
python3 -B stig-remediations/nessus_summary.py "$private_before" \
  --target "$authorized_target" --origin authorized-live --followup "$private_after"
```

These commands are for an already authorized private export; they do not authorize downloading one. Keep output private until review. The default origin is `synthetic`. Exit 0 means extraction succeeded, **not** that the baseline is valid; exit 2 rejects unsupported, ambiguous or out-of-scope input.

The parser accepts one IP-addressed host in one report, UTF-8, a regular non-symlink file of at most 16 MiB and no DTD/entities. An observed service export splits one host into three `ReportHost` fragments. Multiple fragments require nonempty host IP, host UUID, start and end metadata and identical full host-property maps; every fragment name must match the authorized target. Empty reports, extra hosts/reports, nested or excessive fragments, repeated cross-fragment items, identity conflicts and duplicate scalar fields fail closed. Only exact prepared control IDs at the beginning of the check name are mapped. Duplicate findings are ambiguous. Missing findings remain unassessed. It recognizes `PASSED` and `FAILED`; other outcomes require manual interpretation. No CSV layout is guessed.

It preserves the original export hash and normalized item/field hashes, not raw output, host identity or arbitrary text. `audit_sha256` hashes the **filename**, not audit content. Rule IDs are read from documented compliance metadata, including the observed `compliance-reference` field. Conflicting IDs stay incompatible, and a revision absent from the export remains unknown instead of being filled from the catalog. The exact observed credentialed-check SMB annotation is recognized without retaining its account; unknown annotations stay unknown. Warning diagnostics, truncation, missing authentication evidence or incompatible mapping block provisional comparisons. The output always claims `unverified`; scan chronology, VM continuity, actual audit content, equivalent settings and provenance need independent review. File hashes prove byte identity, not truthful observations. The 39 parser regression methods use synthetic fixtures; both actual populated compliance exports independently validate complete extraction. Each contains 274 items across three same-host fragments and maps all ten exact V2R11 Rule IDs. Internal ledger review/disclosure gates are unchanged.

## Separately approved diagnostic operation

[tenable_diagnostic.py](tenable_diagnostic.py) is separate from the read-only evidence-client interface. It can prepare, apply, launch once per private batch, and restore an explicitly approved existing scan. It creates no scan, changes no Windows setting, and sends no credential or audit mutation. Every action defaults to offline; `--execute` requires existing protected connection and private batch paths. Use only after approval for the exact scan, target and proposed settings.

The wrapper retains an explicit scanner selection because [Tenable's update guidance](https://developer.tenable.com/docs/update-scan) warns that omitting it can select a default cloud scanner. It checks name, one target, selected audit, Windows credential metadata, disabled schedule and safety options before writes. Original/proposed configuration and hashes stay private. Fresh readback must match before launch; a durable launch-attempt receipt is written before the POST, preventing same-batch retries even after a timeout. A receipt is not proof of launch success: inspect the owned history after an uncertain response. A new batch directory is not authorization for another assessment.

Restore only after the run is terminal. Unexpected credential, audit, schedule, unrelated setting or plugin changes block automatic restoration. Preserve failed attempts and investigate; never delete receipts to retry. The configured diagnostic range is a port-scanner setting, not an enforcement boundary on dependency traffic. The current implementation has 24 synthetic guard cases and three observed apply/launch/restore cycles; it is not a general scan-management system. [Update](https://developer.tenable.com/reference/scans-configure), [launch](https://developer.tenable.com/reference/scans-launch), and [plugin configuration](https://developer.tenable.com/docs/configure-scan-plugins) contracts ground these operations.

## Minimum evidence for the next batches

1. **Baseline:** authorization; private VM identity and target mapping; scanner ID/status/source; exact scan/history; start/end UTC; assessed-host count; credentialed checks and registry access; audit filename/revision/content hash when available; per-control rule, status, applicability, expected/actual state; export hash and completeness. A missing field stays unknown.
2. **Change:** select genuine failed controls after revision review. Record source hashes, policy authority, original value/snapshot, preview, approved execution, `Status`, `Changed`, exit code, local verifier and effective-policy/side-effect checks. Preserve errors and do not apply unapproved controls.
3. **Follow-up:** same VM, scanner, audit and comparable settings; a new identified scan history with successful authentication and complete control results. Preserve both exports and any configuration differences.
4. **Review:** reconcile extracted observations with original evidence, populate the existing internal schema, link sanitized per-control reports and obtain independent review and disclosure approval. No extraction, matching registry value or zero-vulnerability count establishes external acceptance.
